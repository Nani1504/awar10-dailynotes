In Terraform, meta-arguments are special arguments that control how Terraform creates, manages, updates, and deletes infrastructure resources. 

So primarily we have five meta arguments:
1. count
2. depends_on
3. for_each
4. provider
5. life cycle
	5.1 create_before_destroy
	5.2 prevent_destroy
	5.3 ignore_changes

1. count:
I use the count meta-argument when I want to create multiple instances of the same resource using a single resource block. It accepts a number and creates resources based on that number. Terraform identifies each resource using an index starting from zero. We can also use count with conditional expressions to decide whether a resource should be created.

Example:

resource "aws_instance" "web" {
  count         = 3
  ami           = "ami-0123456789abcdef0"
  instance_type = "t3.micro"

  tags = {
    Name = "web-server-${count.index}"
  }
}

Explanation:

Terraform creates three EC2 instances.
count.index generates indexes 0, 1, and 2.
Resource addresses will be:
aws_instance.web[0]
aws_instance.web[1]
aws_instance.web[2]

Real-time scenario: If I need three identical EC2 instances for an application, I use count instead of writing three separate resource blocks.

2. depends_on:
I use the depends_on meta-argument to define explicit dependencies between Terraform resources. Terraform automatically identifies dependencies when one resource references another resource's attributes. However, sometimes a dependency exists even when there is no direct reference between resources. In that situation, I use depends_on to ensure Terraform creates resources in the required order.

Example:

resource "aws_s3_bucket" "app_bucket" {
  bucket = "my-application-data-bucket"
}

resource "aws_instance" "web" {
  ami           = "ami-0123456789abcdef0"
  instance_type = "t3.micro"

  depends_on = [
    aws_s3_bucket.app_bucket
  ]
}

Explanation:
First, Terraform creates the S3 bucket.
After that, Terraform creates the EC2 instance.
Even though the EC2 instance doesn't directly reference the S3 bucket, we explicitly establish the dependency.

Real-time scenario: Suppose my application requires an IAM policy or another infrastructure component to be ready before deployment. I can use depends_on to establish the required ordering.

3. for_each:
I use the for_each meta-argument when I want to create multiple resources based on a map or set of strings. Unlike count, which identifies resources using numerical indexes, for_each identifies resources using unique keys. It is particularly useful when resources have different configurations or names. It also provides more predictable resource identification when adding or removing individual resources.

Example:
resource "aws_s3_bucket" "buckets" {
  for_each = toset([
    "dev",
    "stage",
    "prod"
  ])

  bucket = "my-company-${each.key}"
}

Explanation:
Terraform creates three S3 buckets:
my-company-dev
my-company-stage
my-company-prod

Here:
each.key represents the current key.
each.value represents the corresponding value.

Real-time scenario: Suppose I need to create S3 buckets for development, staging, and production environments. I prefer for_each because each resource has a meaningful identifier instead of a numerical index.

count vs for_each:

count	                               for_each
Uses numerical indexes           	Uses unique keys
Accepts a number	                Accepts a map or set of strings
Access using count.index	        Access using each.key
Suitable for identical resources	Suitable for individually identified resources

4. provider:
I use the provider meta-argument when I need to manage resources using a specific provider configuration. For example, if I have multiple AWS accounts or regions, I can configure multiple AWS providers with different aliases. Then I can associate individual resources with the required provider using the provider meta-argument. This is useful for managing infrastructure across multiple AWS accounts and regions from a single Terraform configuration.

Example:
provider "aws" {
  region = "ap-south-1"
}

provider "aws" {
  alias  = "us"
  region = "us-east-1"
}

resource "aws_instance" "mumbai" {
  ami           = "ami-0123456789abcdef0"
  instance_type = "t3.micro"
}

resource "aws_instance" "virginia" {
  provider      = aws.us
  ami           = "ami-0123456789abcdef0"
  instance_type = "t3.micro"
}

Explanation:
First EC2 instance gets created in Mumbai (ap-south-1).
Second EC2 instance gets created in Virginia (us-east-1).
provider = aws.us tells Terraform to use the aliased provider configuration.

Real-time scenario: If my organization maintains separate AWS accounts or regions for development and production, I can use provider aliases to manage infrastructure in both environments.

5. lifecycle:
I use the lifecycle meta-argument to control how Terraform creates, updates, and destroys infrastructure resources. It provides additional control over resource lifecycle operations. It is particularly useful when managing critical resources such as EC2 instances, RDS databases, and S3 buckets. The three lifecycle rules I commonly use are create_before_destroy, prevent_destroy, and ignore_changes.

5.1 create_before_destroy:
I use create_before_destroy when I want Terraform to create a replacement resource before destroying the existing resource. Normally, Terraform may destroy the existing resource first and then create its replacement. By enabling this option, Terraform creates the new resource first and destroys the old one after successful creation. This helps reduce downtime during infrastructure updates, provided the resource and surrounding architecture support replacement without conflicts.

Example:

resource "aws_instance" "web" {
  ami           = "ami-0123456789abcdef0"
  instance_type = "t3.micro"

  lifecycle {
    create_before_destroy = true
  }
}

Real-time scenario:

Suppose I need to replace an EC2 instance because of an AMI update. Instead of destroying the existing instance first, Terraform creates the replacement and then removes the old instance.

5.2 prevent_destroy:
I use prevent_destroy to protect critical infrastructure resources from accidental deletion through Terraform. When this option is enabled, Terraform generates an error if a plan includes destroying that resource. It is particularly useful for production databases, important S3 buckets, and other business-critical infrastructure. It acts as a safeguard against accidental destruction during Terraform operations.

Example:

resource "aws_db_instance" "production" {
  identifier        = "production-db"
  engine            = "mysql"
  instance_class    = "db.t3.micro"
  allocated_storage = 20

  lifecycle {
    prevent_destroy = true
  }
}

Real-time scenario:

Suppose I am managing a production RDS database. I don't want anyone accidentally deleting it through Terraform. So I enable prevent_destroy = true.

Important interview point: If someone tries to destroy this resource through Terraform, the operation fails while the lifecycle rule remains in the configuration. Removing the resource block entirely also removes this protection, so it is not a complete deletion safeguard.

5.3 ignore_changes:
I use ignore_changes when certain resource attributes are modified outside Terraform, and I don't want Terraform to overwrite those changes during subsequent deployments. For example, suppose Terraform creates an EC2 instance with specific tags, but another automation tool or operations team updates those tags. Terraform may detect the difference during the next plan. By using ignore_changes, I can tell Terraform to ignore changes to selected attributes and avoid unnecessary updates.

Example:

resource "aws_instance" "web" {
  ami           = "ami-0123456789abcdef0"
  instance_type = "t3.micro"

  tags = {
    Name = "web-server"
    Environment = "dev"
  }

  lifecycle {
    ignore_changes = [
      tags
    ]
  }
}

Explanation:
Terraform initially creates the EC2 instance with the specified tags.
Later, an operations team manually updates the tags.
Terraform ignores subsequent changes to the tags attribute.
It continues managing other resource attributes normally.

Real-time scenario: If an external automation tool manages EC2 tags, I can use ignore_changes to prevent Terraform from continuously trying to revert those tag changes.

Quick interview revision:
Meta-argument	                     Purpose	                       Real-time use case
count	                     Creates multiple resources          	3 identical EC2 instances
for_each	                 Creates resources using keys	        Dev, stage, prod buckets
depends_on	                 Controls dependency ordering	        IAM policy before dependent resource
provider	                 Selects provider configuration	        Multiple AWS regions/accounts
create_before_destroy	     Creates replacement first	            EC2 replacement
prevent_destroy	Prevents     accidental destruction	                Production RDS
ignore_changes	Ignores      selected attribute changes	            Externally managed EC2 tags

One important interview distinction:
count and for_each → How many resources should Terraform create?
depends_on → In what order should Terraform create resources?
provider → Which provider configuration should Terraform use?
lifecycle → How should Terraform handle resource creation, updates, and deletion?

parallelism in terraform:

So by default Terraform can create, update, and destroy resources concurrently to maximise the deployment speed. For that it has a parallelism limit: 
it can perform 10 operations concurrently by default.

We can adjust this by using `terraform apply --parallelism=3`.

Below is the best practise checklist to maintain a Terraform state file:
1. Always use a remote backend S3 for a team's project.
2. Enable S3 versioning.
3. Enable S3 bucket locking with governance or compliance mode.
4. Enable `use_lockfile = true` to prevent concurrent changes from applying.
5. Set `prevent_destroy = true` on resources including statefile storage s3 bucket.
6. Block public access on the S3 bucket.
7. One more important point: never ever manually edit the Terraform state file.

--> Use "Terraform force-unlock" When we really want to unlock the file in emergency cases or in special scenarios.

Modules: terraform modules help us to organise infrastructure code into a clean scalable folder structure. A module is a collection of related resources that are managed together.

Using modules in our project can improve readability, reduce duplication, and help reusability across teams or environments. 


We will have a root module and child modules.

Root module: This is a top-level directory where Terraform commands are executed. All .tf files in the directory collectively form the root module.

Child modules: Modules called or referred to by the root module. They help break down infrastructure into smaller maintainable components. For example we can have one child module for EC2 and another child module for S3. 


Project/
├── main.tf
├── modules
│   ├── ec2
│   │   ├── main.tf
│   │   ├── outputs.tf
│   │   └── variables.tf
│   └── s3
│       ├── main.tf
│       ├── outputs.tf
│       └── variables.tf
└── variables.tf


--> Whenever we are using a module we do not need to define a provider block in the child modules. We can define it only once in the root module. That is sufficient. 
--> Provider block always should be in the root module only. 
--> Run `terraform init` whenever we add any new module. 
--> Each child and root module requires a "variables.tf" file, even if you have not set up any default values. The file and variables should be present. 

In Terraform you must define variables in both root and child modules because each module operates in its own isolated scope. Terraform handles variables as arguments, like in traditional programming functions. A child module cannot see variables in the root module unless we explicitly declare them in the child and pass them down by the way. 


========================


We have four types of modules:
1. Local path: where we can write and we can call it.

module "s3" {
  source      = "./modules/s3"
  bucket_name = var.bucket_name
}


2. Git repository: We can have all our code in the Git repository. We can call it.

module "vpc" {
	source = "git::https://github.com/avizway1/module-name.git"
}

3. Terraform registry: We can provide the source for a Terraform module. We can run it. 

module "iam_user" {
  source = "terraform-aws-modules/iam/aws//modules/iam-user"
  name   = "avinash"
}

4. For a private registry where it will be available within the network, you can call it.

module "network" {
	source = "app.terraform.io/mycompanyname/network/aws"
	version = "1.10.1"
}
